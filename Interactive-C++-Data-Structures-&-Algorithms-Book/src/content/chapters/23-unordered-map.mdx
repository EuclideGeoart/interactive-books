<Section id="intuition" number="02" title="Equality decides identity; hashing narrows the search." kicker="INTUITION">

Two objects can occupy different native addresses and still be equal keys. For PointKey, equality compares coordinate values. Hashing must be consistent with that identity: equivalent keys must have equal hashes, while unequal keys may collide. A custom equality predicate must describe a stable equivalence relation. [C++ draft: unordered requirements](https://eel.is/c++draft/unord.req#general)

The examples explicitly supply a teaching string hash. The number displayed is that supplied functor's result, not a predicted value of `std::hash<std::string>`. No modulo formula is asserted for the library's bucket selection. PointHash is a separate, deliberately simple example over integer coordinates.

</Section>
<Section id="memory" number="03" title="An iterator and an element reference serve different purposes." kicker="STRUCTURE / MEMORY LAYOUT">

An iterator participates in traversal. A reference identifies an element. Rehash invalidates iterators but preserves pointers and references to elements; erase invalidates handles to erased elements. No specific node layout, growth sequence or iteration order is assumed here. [C++ draft: invalidation](https://eel.is/c++draft/unord.req#general)

The lab saves a conceptual iterator and reference to the first starting key. Membership cards stay separate from those handles, so an invalid iterator is never portrayed as permission to read freed data. A call that assigns an existing mapped integer visibly changes that value while the element remains present.

</Section>

<Section id="invariants" number="07" title="Hash and equality must agree on what a key means." kicker="INVARIANTS">

The central implication is `a == b ⇒ hash(a) == hash(b)`. The reverse is unnecessary. Equal coordinate pairs must produce equal PointHash values. Distinct pairs such as (1,2) and (0,33) collide under this example but remain distinct keys because equality compares both coordinates.

Key identity must not depend on changing external state. If a custom equality rule ignores y but the hash continues to include it, two keys deemed equal can begin in different hash groups. Do not insert such a mismatched pair into a real map to see what happens; test the predicate/hash implication separately, as the Break-It panel does.

</Section>
<Section id="complexity" number="08" title="Reserve elements; rehash buckets." kicker="COMPLEXITY / CAPACITY EXPLORER">

Use the Reserve, Rehash and Set load hint tabs above, varying the numeric request and starting membership. The display reports size, a justified bucket lower bound, and an exact fractional upper bound for load factor when available. It does not round a bound downward or invent a bucket count. No comparison counter is shown because the standard-library implementation is not being executed in the browser.

After rehash(n), bucket_count is at least n and sufficient for size/max_load_factor. Reserve(n) is equivalent to rehash(ceil(n/max_load_factor())). The maximum-load setter supplies a hint; query the getter for the accepted value and do not infer an immediate rebuild. [C++ draft: hash policy](https://eel.is/c++draft/unord.req#general)

Lookup and single-key mutation have average constant-time expectations and linear worst cases. Rehash has average linear and worst quadratic complexity. [C++ draft: complexity requirements](https://eel.is/c++draft/unord.req#general)

These bounds do not include a promise that your hash is cheap. For a long string, evaluating the supplied function consumes its characters. Reservation can move growth work to a deliberate phase; it does not cure a pathological hash function or eliminate all future allocations. This chapter's teaching strings are bounded in length to keep the example focused.

</Section>

<Section id="analogy" number="10" title="The catalog entry can stay while the index changes." kicker="REAL-WORLD ANALOGY">

A catalog's indexing system may be reorganized without changing the records it indexes. An old traversal position can become unusable even though a particular record remains. Removing that record is a different event: references to it no longer identify a live element. The analogy separates index organization from membership without specifying how either is implemented.

</Section>
<Section id="engineering" number="11" title="Choose the container for the workload and guarantees." kicker="ENGINEERING INSIGHT">

Use unordered_map when key-based access matters and ordering does not. Consider an ordered map when sorted traversal or range queries dominate; a sorted vector or small linear collection can be attractive when data is tiny or changes rarely. Compare memory overhead, iteration locality, key size, adversarial inputs and reference requirements under the actual workload.

Many implementations use node-based storage, but that is an implementation tendency, not a layout promised by this visualization. Measure the selected standard library, allocator and hash policy. Do not transfer the exact tombstone, Robin Hood, resize or relocation rules from the preceding teaching containers to an unrelated library container.

</Section>
