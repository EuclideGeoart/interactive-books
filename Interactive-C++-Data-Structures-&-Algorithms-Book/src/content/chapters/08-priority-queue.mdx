<Section id="intuition" number="02" title="Define the ADT before choosing storage." kicker="THE CONTRACT">

`insert(value, priority)` adds an entry. `peek()` returns the next entry without removal. `extract()` returns and removes that entry. Both `empty()` and `size()` describe membership. None of these promises requires a sorted array or a tree.

A FIFO queue promises the oldest arrival next. A deque exposes both endpoints. A ring buffer changes their storage mechanics. **A priority queue changes the removal policy itself.** Higher-number-first and lower-number-first are both useful conventions: urgency often increases with the number, while the earliest scheduled timestamp is the smallest number.

Ties are a separate design decision. This chapter explicitly chooses FIFO among equal priorities. Other APIs may choose arbitrary order. Stability is not inherent in the words “priority queue,” and should never be assumed without an interface guarantee.

</Section>

<Section id="memory" number="03" title="One contract, several representations." kicker="STRUCTURE & STORAGE">

The canonical `PriorityQueue` stores entries in an unsorted `std::vector<Entry>`, preserving arrival order. Insertion appends. Peek scans for the best priority. Extraction scans, saves the chosen entry, and erases it; later entries shift left without changing relative order. Storage indices may change after extraction and are not persistent IDs.

A sorted array instead pays during insertion so the best entry is already at an accessible endpoint. Keep that endpoint at the **back** to remove without shifting. A sorted linked list has different allocation and locality costs; even with O(1) insertion at a known position, finding that position is O(n). An unsorted linked list likewise scans to find the best entry, despite cheap relinking once found.

A binary heap offers a third balance: efficient repair after insert/extract and constant-time access to the next entry. Chapter 9 explains its mechanics. Here, compare the observable costs without assuming that the ADT itself is a heap.

</Section>

<Section id="implementation" number="05" title="A complete stable, unsorted implementation." kicker="CANONICAL C++20">

`Entry` contains two integers. The queue owns its vector and relies on RAII for destruction. Copy construction and assignment are explicitly defaulted and produce independent value copies. Move construction and assignment are explicitly defaulted: vector storage transfers according to standard container semantics, and the source remains valid with unspecified contents. No code assumes a moved-from queue is empty.

`peek()` returns an entry by value, so callers do not retain a reference into storage that a future insertion or erase could invalidate. Both Peek and Extract throw `std::underflow_error` when empty. Append can throw on allocation failure; the prior queue is preserved for this integer entry type. After a successful scan, the integer copy and erase path does not throw.

<Section id="invariants" number="07" title="Priority, stability, and guarded access." kicker="CHECK THE PROMISE">

The selected candidate must outrank every other entry under the chosen direction. Equal priorities must retain arrival order. Empty storage must never be indexed for a result. Our scan checks emptiness first and only reads indices strictly below `size()`.

The ranked diagram is a derived view, not a second mutable container. The comparator uses priority only; the stable index tie-break in the display mirrors the native scan's “keep the earlier candidate” rule. There is no requirement that the underlying vector be sorted.

<Section id="complexity" number="08" title="Where should the work happen?" kicker="COMPLEXITY EXPLORER">

<PriorityExplorer />

An unsorted array performs n−1 priority comparisons for nonempty Peek or Extract. Extraction may additionally shift n−1 entries, so its overall cost remains O(n). Appending takes O(1) with spare capacity and amortized O(1) over many inserts; a particular reallocation can move O(n) entries.

Sorted storage does up to n shifts during insertion, but Peek and removal from the back take O(1). Heap insertion/extraction repairs at most logarithmically many levels; a vector-backed heap insertion still has the same occasional O(n) reallocation caveat. The count model compares kinds of work, not measured timings or exact CPU cost.

<Callout title="Choose from the workload.">If almost all operations are inserts and reads are rare, unsorted storage can be reasonable. If the next result is read repeatedly between occasional inserts, moving work to insertion may help. A heap balances frequent inserts and extractions without fully sorting all entries.</Callout>

</Section>

<Section id="analogy" number="10" title="A dispatcher with an explicit rule." kicker="REAL-WORLD ANALOGY">

A dispatcher receives jobs in arrival order but chooses the most urgent waiting job. Equal urgency follows arrival order. A later urgent job can overtake older low-priority work. If urgent jobs keep arriving, low-priority work can starve; the data structure does not automatically provide fairness or aging.

</Section>

<Section id="engineering" number="11" title="Scheduling is more than ordering." kicker="ENGINEERING INSIGHT">

An event simulator often uses a lower-first queue keyed by event time. A task scheduler might use higher-first urgency. Dijkstra and best-first pathfinding choose the smallest current distance or estimate. Their correctness depends on the algorithm's surrounding rules, not merely on storing priorities.

This implementation does not expose decrease-key, cancellation, or mutable entry handles. One practical pathfinding strategy inserts a new distance and discards stale entries when removed; that changes memory use and requires an external “best known distance” check. Stable ties make experiments reproducible but do not replace that check. Thread safety, real-time allocation constraints, and fairness are separate engineering requirements.

</Section>
