To search for 62, compare against 50. It is not equal and is larger, so skip the entire left subtree and follow right to 75. It is smaller than 75, so go left to 60. It is larger than 60, so go right to 62. Equality ends the search. Each equality and ordering test appears separately in the lab.

The rule applies to **all descendants**, not only immediate children: every key in the left subtree is smaller than its ancestor, and every key in the right subtree is larger. This global range restriction makes pruning a whole subtree sound.

<Section id="intuition" number="02" title="Choose the meaning of equality first." kicker="THE INTUITION">

This book's numeric search trees are **sets of integers**. Inserting an existing value returns false and changes no links, values, or node lifetimes. Chapter 10's unordered BinaryTree may contain repeated values; the BST introduces a stronger contract. The same set policy applies to the balanced numeric trees later in Part III.

A strict successor is the smallest stored key greater than the query. A strict predecessor is the largest key less than it. These APIs also work for a query absent from the tree: successor(61) is 62 in the preset. Missing neighbors return null, as do minimum and maximum on an empty tree.

</Section>

<Section id="memory" number="03" title="Ordering needs no extra Node field." kicker="STRUCTURE / MEMORY LAYOUT">

The actual Node still stores value, left, and right, with no parent pointer, cached height, color, or subtree count. `root_` owns the hierarchy through child links. Insertion chooses a null child position by comparisons instead of filling the first level-order vacancy.

The same input keys can have very different shape under different insertion orders. Separate allocations preserve addresses while links and values change. A search returns a const, non-owning observer; callers must not keep using it after that node is erased or its tree dies. Two-child erase may change the observed node's value without changing its address, a distinction developed in Chapter 13.

</Section>

<Section id="implementation" number="05" title="Reuse ownership without exposing the wrong insertion." kicker="C++ IMPLEMENTATION">

`BinarySearchTree` privately inherits the Chapter 10 representation. It publicly exposes root and clear, and implements ordered operations itself. Private inheritance keeps unordered `append` out of the BST's public API; exposing it would let a caller violate ordering without any comparison. The `using` declarations expose the Node type and selected observer/cleanup functions, not duplicate storage.

The base deletes copy and move operations, so the BST is also noncopyable and nonmovable. Its inherited destructor performs iterative clear. Allocation failure during insert occurs before publishing a link; the old tree remains intact. Searches and erase allocate no memory. All operations use ordinary integer comparisons with no custom comparator abstraction.

<Section id="pointer-trace" number="06" title="A cursor selects; a slot can publish." kicker="CODE + VISUALIZATION POINTER TRACE">

Search changes a local `current` pointer. The owning links remain unchanged. After equality fails, the less-than comparison determines exactly one next field. When current becomes null, the next loop guard fails and the function returns null; no dead field is read.

Insert keeps `Node** slot`, the address of a root or child pointer. Moving slot left or right changes a local only. After a null vacancy is found, construction creates a new live Node with null children; `*slot = fresh` changes one owning link. No recursive return sequence or parent-pointer write is hidden behind that assignment.

Successor saves current as candidate only if current's value is strictly greater, then searches left for a smaller eligible key. Otherwise it goes right. Predecessor reverses those directions. On return the candidate observer survives only as the function's returned value; the local name itself leaves scope.

</Section>

<Section id="invariants" number="07" title="Ranges compose from the root." kicker="INVARIANTS">

All Chapter 10 ownership rules still apply: live targets, no cycles or shared ownership, and complete reachability at boundaries. The ordering checker carries an open lower and upper bound down the entire subtree. A node can satisfy its immediate parent comparison yet violate a more distant ancestor's range; a local-only check is insufficient.

Strict inequalities prohibit duplicates. During the canonical two-child deletion, copying the successor value temporarily duplicates that key until its original node is detached. The ordering status is pending during that intermediate statement and must pass at completion. Duplicate insertion, in contrast, creates no temporary duplicate at all.

</Section>

<Section id="complexity" number="08" title="A search tree can become a linked chain." kicker="COMPLEXITY EXPLORER">

<TreeComplexity kind="bst" />

Search, insert, minimum, maximum, predecessor, successor, and erase take O(h + 1) work, conventionally written O(h) for nonempty trees. A well-shaped BST has height near log₂ n; sorted insertions can produce height n − 1. The explorer shows the actual maximum-search path for both insertion orders. An ordinary BST makes **no worst-case logarithmic guarantee**.

The lab counts every condition evaluation, including loop guards and equality checks. This is a mechanical work model, not a CPU timing. Iterative ordered operations use O(1) auxiliary space. Nodes use O(n) storage, and clear takes O(n) work with O(1) auxiliary space.

</Section>

<Section id="break-it" number="09" title="Local-looking correctness can hide a global violation." kicker="COMMON MISTAKES / BREAK-IT MODE">

<TreeFoundationsBreakIt ordered />

Put 99 in the left subtree of 50 and inspect the failed range rule. Other faults isolate ownership from sorting: a perfectly ordered sequence of values can still leak a detached subtree or point into freed storage. Restore before running a valid algorithm.

Common mistakes include routing equality inconsistently, assuming every insertion increases size, calling a missing result a valid Node, and claiming O(log n) without a height bound. Empty search, empty min/max, root-only erase, missing deletion, repeated keys, negative values, and absent-query neighbors all have explicit outcomes in this implementation.

</Section>

<Section id="analogy" number="10" title="A set of narrowing numeric signs." kicker="REAL-WORLD ANALOGY">

Imagine signs that split an allowed number range into “smaller” and “larger.” Each turn rules out all numbers on the other side. The signs help only if ranges are truthful. A badly arranged trail with one useful turn at every sign is still linear, even though every sign obeys its local comparison rule.

</Section>

<Section id="engineering" number="11" title="Ordering and balance solve different problems." kicker="ENGINEERING INSIGHT">

Ordered sets support strict neighbors and sorted traversal, useful for interval endpoints, event ordering, and geometric sweep algorithms. A raw unbalanced BST can be reasonable for a controlled shape, but adversarial insertion order can make its performance unacceptable. AVL and red-black trees add rebalancing while preserving the same ordering contract.

Separately allocated nodes spend memory on links and may incur cache misses. A sorted vector often works well for mostly static data despite O(n) insertion shifts. Choose using mutation frequency, locality, iterator/observer stability requirements, and worst-case latency—not only a single complexity label. This teaching container is single-threaded and owns integer values only.

</Section>
