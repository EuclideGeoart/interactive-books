<Section id="intuition" number="02" title="After the last slot, return to zero." kicker="INTUITION">

Chapter 6's naive dequeue copied all survivors toward index 0. A ring buffer leaves them in place and advances head. When an index reaches the final slot, its successor is slot 0: `(4 + 1) % 5 == 0`. The modulo operator gives the remainder after division; for nonnegative indices it keeps the result within `[0,capacity)`.

The array is not physically curved and no pointer jumps between allocations. “Ring” describes reusable indexing. Values can span the end of one contiguous allocation and continue at its beginning. Five live integer objects exist even when no queue members exist.

</Section>

<Section id="memory" number="03" title="Three fields remove an ambiguity." kicker="STRUCTURE & MEMORY LAYOUT">

The count-based design owns five raw slots plus `head`, `tail`, and `count`. Empty is `count == 0`; full is `count == 5`. In both states head can equal tail. Testing equality alone cannot tell them apart.

At a stable boundary, `tail == (head + count) % capacity`. Members are the count slots starting at head, wrapping as needed. The newest element, when nonempty, lives at `(tail + capacity - 1) % capacity`. Adding capacity before subtracting prevents unsigned underflow when tail is zero.

A **sentinel-slot design** instead reserves one position. Empty becomes head equal to tail, and full becomes the next write index equal to head. Five physical slots then hold at most four members. The unused slot moves with the indices; it is not a permanently unused array element. The complete `SentinelRing` alternative appears in the canonical source below.

<Callout title="Raw value is not occupancy." tone="amber">Zero can be a valid queued value, and popped values can remain in unused slots. Neither zero nor any other payload is a reliable empty marker. Membership comes from indices and the chosen full/empty encoding.</Callout>

</Section>

<Section id="implementation" number="05" title="Two encodings, explicit ownership." kicker="CANONICAL C++20">

`RingBuffer` uses count and supports reject or overwrite. `SentinelRing` omits count, reserves one position and rejects on full. Both own their inline `std::array` storage, need no heap allocation during queue operations, and safely support memberwise copy/move. Moving the inline integer storage leaves the source with a valid independent copy of the same value state. No manual destructor or owning raw pointer is needed.

The capacity is a nonzero compile-time constant. Indices use `std::size_t`; this small bound prevents overflow in the additions used for wrap calculations. Pop and endpoint reads guard empty before indexing. Reject-on-full throws `std::overflow_error`; empty operations throw `std::underflow_error`. No successful integer mutation can throw after the guard. The `values()` observer allocates a result vector for tests; it is not the constant-time enqueue/dequeue path.

<Section id="pointer-trace" number="06" title="Writing is not advancing." kicker="CODE ↔ INDEX TRACE">

A successful enqueue writes `data[tail]`, advances tail with modulo, then increments count. Immediately after the write, that slot can still be outside logical membership. After the index advances and before count changes, the endpoint equation is temporarily pending. The physical view exposes these real intermediate states.

Dequeue advances head, then decrements count; it does not clear a payload. On a full overwrite, the first two statements advance head and decrement count to discard the oldest member. Only then does the common enqueue path write, advance tail, and restore full count. There is no hidden “drop oldest” mutation before the displayed source line.

Exact native parity tests instrument the shipped header and compare every tagged condition and statement against all five raw slots and head/tail/count. The teaching model does not claim to execute native C++ inside the browser.

</Section>

<Section id="invariants" number="07" title="Bounds are necessary; policy matters too." kicker="INVARIANTS">

Indices remain within 0…4 and count remains within 0…5. The relation `tail == (head + count) % capacity` must hold before and after a complete operation. Its brief mismatch between two tagged assignments is shown as pending, not a permanent failure. Generic playback does not know any of these circular rules; the ring domain evaluates them.

A reject policy promises unread values remain intact when full. An overwrite policy promises the newest value replaces the oldest in FIFO order. Bounds can remain valid while either promise is broken. The fault experiments therefore diagnose both structural errors and observable policy violations.

</Section>

<Section id="complexity" number="08" title="Scale capacity without scaling the work." kicker="ENCODING & COMPLEXITY EXPLORER">

<RingEncoding />

A successful count-based enqueue performs one payload write, one tail update, and one count update. Dequeue performs one head update and one count update. Full overwrite adds one head and one count update before enqueue. Each path is O(1) structural work; no loop scales with queue length. Front, back, empty, full and size are O(1). The owned storage is O(capacity).

The explorer compares count and sentinel encodings up to 1024 physical slots. Sentinel dequeue needs only one index update; count-based dequeue needs an additional count update but can use every slot. These small instruction counts are not hardware timings. Modulo cost, cache effects and the synchronization required by a real pipeline are separate questions.

</Section>

<Section id="break-it" number="09" title="Cross the boundary deliberately." kicker="COMMON MISTAKES / BREAK-IT MODE">

<RingBreakIt />

Forget modulo and an index leaves the array. Move tail during dequeue and unread order no longer matches head/count. Treat equal indices as empty in a full count-based ring and every member disappears logically. Overwrite without an explicit loss policy and an unread value changes silently. Read from empty and the raw int may be alive but has no queue meaning.

These are bounded model corruptions with explanations, not unsafe native memory accesses. Restore returns the original preset. Use the checked C++ lab above to see the actual guard paths.

</Section>

<Section id="analogy" number="10" title="Numbered trays on a loop." kicker="REAL-WORLD ANALOGY">

Imagine five numbered trays on a serving carousel. The reader marker identifies the oldest occupied tray; the writer marker identifies where a new item belongs. Removing one item does not require moving every other item to a lower tray number. The markers advance, and the numbers repeat after the final tray.

The analogy cannot decide what happens when all trays are occupied. Rejecting a new item and discarding the oldest are different service policies, even though both use the same trays.

</Section>

<Section id="engineering" number="11" title="Bound memory; specify loss." kicker="ENGINEERING INSIGHT">

Audio pipelines, network receive paths, telemetry buffers, event systems and producer/consumer handoffs often benefit from fixed storage and repeated reuse. A latest-samples telemetry history may intentionally overwrite old data; a work queue carrying required jobs should not silently do so. Rejection can trigger backpressure, a drop counter, or an explicit recovery path.

Avoiding per-operation allocation helps predictability in fixed-memory real-time systems, but this example does not establish a hard real-time latency guarantee. It uses exceptions for checked failures and ordinary non-atomic fields. It is **single-threaded**, not a lock-free queue. Shared producer/consumer use requires a separate proof about synchronization, publication and memory ordering.

Circular indexing can also support both endpoints of a deque. Chapter 8 then asks a different question: what if the next item is selected by priority instead of arrival? Chapter 9 supplies a binary heap implementation for that changed access policy.

</Section>
