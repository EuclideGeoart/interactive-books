<Section id="intuition" number="02" title="A match is sufficient; absence requires exhaustion." kicker="THE INTUITION">
To establish presence, one equal key is enough. To establish absence in arbitrary input, every key must be rejected. An unvisited last element could always contain the target. This explains both early termination and the linear worst case.

The contract here is **first match**: scan from index 0 upward and stop immediately on equality. For [2A,1B,2C], searching for 2 returns index 0 and record A. A different traversal direction would implement a different contract. “Return all matches” would require continuing after success and collecting multiple positions.
</Section>

<Section id="memory" number="03" title="Reading an element does not move it." kicker="STRUCTURE / MEMORY LAYOUT">
The input is contiguous indexed storage, like the array-backed structures in earlier chapters. Logical and storage views show the same record order because this algorithm does not mutate it. Each record holds a numeric key and an original identity; the letter is a teaching label for that identity, not part of the comparison.

The algorithm needs an index, a target and a result: O(1) auxiliary space. Our observable implementation additionally owns a copy of the input and its original records so playback and invariants can be checked. Snapshot history is instrumentation, not a claim that ordinary linear search requires O(n) algorithm workspace. `result == -1` represents not found; no array access ever uses that sentinel.
</Section>

<Section id="pointer-trace" number="06" title="Inspection, equality and advancement are separate events." kicker="CODE + VISUALIZATION TRACE">

<Section id="invariants" number="07" title="Every earlier position has already failed equality." kicker="LIVE INVARIANTS">
The live checker verifies conservation of all records, a target-free rejected prefix, and the first-match result. Before an inspection at i, every index below i is known unequal. A successful result must equal the first matching index in the original array; a completed unsuccessful trace must contain no matching record anywhere.

There is no sortedness invariant. Imposing one would unnecessarily restrict a correct algorithm. The result is pending until a match is assigned or exhaustion establishes absence, so the inspector distinguishes a running search from a completed not-found result.
</Section>

<Section id="complexity" number="08" title="Count equality tests instead of timing the animation." kicker="COMPLEXITY EXPLORER">
<SortingComplexity chapter="37" />
For a first match at zero-based position k, the count is k + 1. For a missing target it is n. The best successful case is O(1), and the worst case is O(n). Under a uniform distribution over successful positions, the average is (n + 1) / 2 comparisons; that probability assumption is part of the claim.

These counters model algorithm operations. Playback duration, drawing, input validation, array cloning and JavaScript scheduling are not performance benchmarks. A comparison of search algorithms must also account for preparing and maintaining the ordered domain required by binary search.
</Section>

<Section id="break-it" number="09" title="Do not mistake a boundary for an element." kicker="COMMON MISTAKES / BREAK-IT MODE">
Load empty input and then a missing target in a one-element input. A mistaken `i <= n` guard would attempt to read one past the end. The canonical guard uses a strict bound; the lab never performs that invalid access. Also compare target 2 on the duplicate preset: continuing after success could overwrite the result with a later match, violating the stated first-match policy.

A found index of zero is valid. Testing the result as a boolean would confuse index 0 with failure and −1 with success. Compare explicitly against −1, or design an API using an optional index. This chapter keeps the sentinel visible so its role is unambiguous.
</Section>

<Section id="analogy" number="10" title="Check mailboxes in street order." kicker="REAL-WORLD ANALOGY">
A courier checks labels on a row of mailboxes. Finding the desired label ends the job. Finding no label requires reaching the end of the row. The labels can be in any order; the walk still works. “First matching mailbox” resolves what happens when two labels are identical.
</Section>

<Section id="engineering" number="11" title="A small contiguous scan can be the right tool." kicker="ENGINEERING INSIGHT">
Linear scans are useful for small collections, one-off lookups, and predicates that do not have a matching ordered index. Contiguous access can have favorable locality. Building an index or sorting solely to answer one query can cost more work than the query itself; repeated lookups change that tradeoff.

In an engine, scanning a short material list or command batch is often simpler than maintaining another container. If the input changes during a search, define iterator/index validity and synchronization separately. This deterministic lab owns a snapshot, so concurrent mutation is outside its contract.
</Section>
