<div className="foundations-mini" id="lesson-01"><h3>0.1 — How to read C++ in this book</h3><p>A <strong>type</strong> describes what an expression or object can do. A declaration introduces a name; a definition provides the entity itself. A variable such as <code>Node&#42; p</code> is an object holding a pointer value. An expression such as <code>p-&gt;value</code> produces a value; a statement such as <code>p = nullptr;</code> performs an action. Braces give local names a scope. A function groups statements behind parameters and a return type.</p><p><code>if</code>/<code>else</code> selects a branch; <code>while</code> repeats while its condition is true; a classic <code>for</code> has initialization, condition and update; a range-based <code>for</code> visits each item. <code>break</code> exits the nearest loop or switch, and <code>return</code> exits a function, optionally with a value. In <code>auto x = expression;</code>, the compiler deduces x's type at compile time from the initializer. <code>auto</code> is not dynamic typing.</p><p>Headers included with <code>#include</code> supply declarations and, for these header-based examples, definitions. <code>namespace foundations</code> keeps names separate from other chapters. Use <code>object.value</code> for an object and <code>pointer-&gt;value</code> for a pointer to one. Compilation checks syntax, types and templates; runtime executes operations on particular values. Neither stage can make an invalid dereference safe.</p><UsedLater numbers={['01','04','12']} /></div>

<Section id="objects" number="02" title="Storage can outlive an object." kicker="0.2 · VALUES, STORAGE AND LIFETIME">

<div className="foundations-mini" id="lesson-02"><h3>0.2 — Objects, storage and scope</h3><p>Storage is a region of memory suitable for an object. An object's <strong>lifetime</strong> begins after its initialization or construction and ends when it is destroyed. The same storage may later hold another object. A block can exist with no live <code>T</code> inside it, as the memory pool and object pool demonstrate.</p><p>A local object usually has automatic storage duration: leaving its scope destroys it. A dynamic allocation survives until its owner releases it. <Section id="pointers" number="03" title="An address is a route, not ownership." kicker="0.3–0.4 · POINTERS AND OWNING SLOTS">

<div className="foundations-mini" id="lesson-03"><h3>0.3 — Pointers, references and nullptr</h3><p><code>Node&#42; p</code> holds an address or <code>nullptr</code>. <code>&amp;a</code> obtains A's address; <code>&#42;p</code> accesses the pointed-to object; <code>p-&gt;value</code> is shorthand for <code>(&#42;p).value</code>. <div className="foundations-mini" id="lesson-04"><h3>0.4 — Pointer-to-pointer and reference-to-pointer</h3><p><code>Node&#42;&#42; slot</code> points to a pointer field, not directly to the node. If <code>slot = &amp;root</code>, then <code>&#42;slot = replacement</code> changes <code>root</code>. <Section id="types" number="04" title="Types make invariant boundaries." kicker="0.5–0.6 · STRUCTS, CLASSES AND CONSTRUCTION">

<div className="foundations-mini" id="lesson-05"><h3>0.5 — struct, class and encapsulation</h3><p>A <code>struct</code> groups members, public by default. A <code>class</code> defaults to private. Both support constructors, member functions, nested types and access control. A list's private <code>head</code> prevents callers from bypassing the operations that preserve reachability. <code>this</code> refers to the current object inside a member function. Forward declarations allow pointers or references to a type before its full definition. A base class provides members a derived class can reuse or extend. <code>class BinarySearchTree : private BinaryTree</code> reuses an implementation without exposing the base interface publicly; a public <code>using BinaryTree::member;</code> can selectively re-expose an inherited name. If a derived object may be deleted through a base pointer, the base needs a virtual destructor so the derived destructor also runs.</p><UsedLater numbers={['01','05','10','23']} /></div>

<div className="foundations-mini" id="lesson-06"><h3>0.6 — Constructors and destructors</h3><p><code>Node(int n) : value(n), next(nullptr) {'{}'}</code> initializes members before the constructor body. A default constructor takes no arguments; a parameterized one uses arguments. A destructor such as <code>~List() {'{'} clear(); {'}'}</code> runs when the owning object ends its lifetime. Members are destroyed after the destructor body, in reverse declaration order. For an automatic owner this happens predictably at scope exit, including exception unwinding. A destructor does not automatically follow a borrowed pointer to delete its target. A one-argument constructor can otherwise permit an implicit conversion; <code>explicit</code> blocks that conversion while direct construction remains available. A default argument supplies an omitted parameter, as in <code>explicit BinaryHeap(bool max_heap = true)</code>: callers may write <code>BinaryHeap{'{}'}</code> or pass a value.</p><UsedLater numbers={['01','04','05','53']} /></div>

</Section>

<Section id="ownership" number="05" title="One owner decides when a resource ends." kicker="0.7–0.10 · RAII, ALLOCATION AND VALUE SEMANTICS">

<div className="foundations-mini" id="lesson-07"><h3>0.7 — RAII and unique ownership</h3><p>RAII ties cleanup to an owning object's destructor. A list owns its allocated nodes; a traversal pointer borrows them. <code>std::unique_ptr&lt;T&gt;</code> owns one object and releases it automatically. Moving a <code>unique_ptr</code> transfers its resource; copying is disabled. A raw <code>Node&#42;</code> obtained from <code>get()</code> is still borrowed. Intrusive hooks show another pattern: a list owns membership relationships while a separate owner retains the objects.</p><UsedLater numbers={['01','05','20','53']} /></div>

<div className="foundations-mini" id="lesson-08"><h3>0.8 — new/delete and matching array allocation</h3><p><code>new Node(10)</code> allocates suitable storage, constructs a node and returns a pointer. <code>delete p</code> runs its destructor and releases the allocation. It does not remove the pointer variable: <code>p</code> now dangles. <code>new T[n]</code> constructs an array and requires <code>delete[]</code>; the scalar and array forms must match. Leaks, double deletion, deleting a nonmatching allocation and use after free are errors. Prefer a clear owner, or a standard owner type when manual allocation is unnecessary.</p><SourceCode source={source} region="new-delete" /><UsedLater numbers={['01','02','04']} /></div>

<div className="foundations-mini" id="lesson-09"><h3>0.9 — Placement construction and alignment</h3><p><code>sizeof(T)</code> measures the storage needed for T; <code>alignof(T)</code> gives its alignment. <code>alignas(T)</code> can request suitably aligned byte storage. Placement <code>new (memory) T(args...)</code> and C++20 <code>std::construct_at</code> start an object lifetime in existing storage. An explicit destructor call or <code>std::destroy_at</code> ends it without releasing that storage. Alignment 4 at illustrative address 5 needs three bytes of padding before address 8.</p><p>The pool first reserves a slot, then constructs T. If construction throws, no T lifetime completed and only storage needs rollback. Unions in Chapter 4 overlay a free-link member and T storage; only the active member may be accessed. For raw storage, <code>void&#42;</code> does not promise a live T; a cast alone cannot create one. Its checked address lookup compares candidate block addresses rather than subtracting unrelated pointers.</p><p>Chapter 51 uses <code>std::byte</code> and <code>std::memcpy</code> to write a free-link representation into raw storage; copying bytes does not by itself make an arbitrary T live. <code>std::addressof</code> obtains an address even if a type overloads <code>operator&amp;</code>. <code>static_cast</code> expresses a checked type conversion where the language permits it; <code>reinterpret_cast</code> exposes a low-level representation and cannot bypass alignment or lifetime rules. Type traits such as <code>std::is_nothrow_destructible_v&lt;T&gt;</code> let a pool reject unsupported T types at compile time. The <code>std::uintptr_t</code> address check in Chapter 4 is validation-only.</p><FoundationsLab kind="alignment" /><UsedLater numbers={['04','51','52','53']} /></div>

<div className="foundations-mini" id="lesson-10"><h3>0.10 — Copy, move and deleted operations</h3><p>A copy of a value-owning vector creates independent elements. A shallow copy of a raw-owning list would make two owners delete the same chain, so Chapter 1 deletes its copy operations. A move transfers ownership into a new object; a moved-from object remains valid, with a type-specific state. <code>std::move</code> requests move treatment; it does not move bytes by itself. <code>= default</code> asks the compiler for an operation, while <code>= delete</code> forbids it.</p><p>The Rule of Zero favors member types that manage resources themselves. A type that manually manages a resource must deliberately choose its destructor, copy and move policy (the Rule of Five). The canonical <code>Buffer</code> deep-copies its <code>unique_ptr</code> payload, then uses defaulted moves.</p><FoundationsLab kind="copy" /><UsedLater numbers={['01','06','20','21','36']} /></div>

<Section id="contracts" number="06" title="Reject invalid work before changing state." kicker="0.11–0.12 · CONST, ASSERTIONS AND EXCEPTIONS">

<div className="foundations-mini" id="lesson-11"><h3>0.11 — const, noexcept, static_assert and assert</h3><p><code>int top() const</code> promises not to modify the object through that member function's ordinary <code>this</code> access. <code>const T&amp;</code> borrows a read-only view. <code>noexcept</code> is an exception contract; throwing through it terminates the program. <code>static_assert</code> rejects a failed compile-time condition. <code>assert</code> diagnoses a programmer invariant at runtime in builds where assertions are enabled; it may be compiled out and must never be the only check for untrusted or ordinary user input.</p><UsedLater numbers={['03','04','06','53']} /></div>

<div className="foundations-mini" id="lesson-12"><h3>0.12 — Exceptions and guard-before-mutation</h3><p><code>throw</code> reports an error to a caller, which may use <code>try</code>/<code>catch</code>. A full stack throws <code>std::overflow_error</code> <em>before</em> changing its state; an empty stack throws <code>std::underflow_error</code>. Check preconditions first, prepare fallible allocations before publishing links, and clean up reserved storage if construction fails. The strong guarantee means an operation that fails leaves the observable state unchanged; the basic guarantee preserves a valid state but may retain completed changes, as B-tree splits can.</p><FoundationsLab kind="contracts" /><UsedLater numbers={['02','04','10','16','52']} /></div>

<Section id="containers" number="07" title="Extent, capacity and ownership are different." kicker="0.13–0.16 · CONTIGUOUS STORAGE AND VIEWS">

<div className="foundations-mini" id="lesson-13"><h3>0.13 — std::array and std::vector</h3><p><code>std::array&lt;int, 5&gt;</code> has five existing elements; a logical stack may use only a prefix. Popping that stack changes its count or sentinel, not the lifetime of the unused <code>int</code> slots. <code>std::vector</code> owns a dynamic contiguous allocation: <code>size()</code> counts live elements and <code>capacity()</code> counts total element slots available without reallocation. <code>push_back</code> adds one element; <code>pop_back</code> removes the last; <code>reserve(n)</code> requests capacity without changing size; <code>resize(n)</code> changes size and constructs or destroys elements. Index only within <code>[0, size())</code>.</p><FoundationsLab kind="vector" /><p>When vector growth reallocates, all old element pointers, references and iterators, including <code>end()</code>, are invalid. A capacity increase is permitted to choose an implementation-specific new capacity. A vector is contiguous, never a linked chain. Chapter 23 has a different rule: rehashing <code>std::unordered_map</code> invalidates iterators but preserves references and pointers to surviving elements.</p><UsedLater numbers={['02','09','16','23','54','56']} /></div>

<div className="foundations-mini" id="lesson-14"><h3>0.14 — span, string and string_view</h3><p><code>std::span&lt;const int&gt;</code> is a non-owning window onto contiguous elements. <code>std::string</code> owns character storage; <code>std::string_view</code> borrows a character range. A view must not outlive its source, and vector reallocation can invalidate a span into that vector. A view neither copies the data nor keeps an owner alive. The trie reads a bounded word through <code>string_view</code>; the arena returns byte spans into storage it controls.</p><UsedLater numbers={['17','18','52']} /></div>

<div className="foundations-mini" id="lesson-15"><h3>0.15 — optional means explicit absence</h3><p><code>std::optional&lt;std::size_t&gt;</code> can hold index zero or no index at all. Check engagement before reading its value. Hash lookups use this distinction; dynamic programming additionally distinguishes “unknown” from “known unreachable.” An intentional signed sentinel such as −1 is safe only when code keeps it out of unsigned indexing.</p><FoundationsLab kind="optional" /><UsedLater numbers={['20','21','49','55']} /></div>

<div className="foundations-mini" id="lesson-16"><h3>0.16 — enum class names states</h3><p><code>enum class SlotState {'{'} Empty, Occupied, Tombstone {'}'}</code> creates scoped values such as <code>SlotState::Occupied</code>. Named phases make legal transitions visible; a tombstone is not the same as a never-used empty hash slot. <Section id="generic" number="08" title="Syntax carries the algorithm's policy." kicker="0.17–0.19 · OPERATORS, CALLABLES AND TEMPLATES">

<div className="foundations-mini" id="lesson-17"><h3>0.17 — Operator overloading</h3><p>For a class type, <code>a == b</code> can call a matching overloaded <code>operator==</code> (for example, a member <code>a.operator==(b)</code>). The C++20 defaulted equality in <code>PointKey</code> compares its members. A manual equality could compare <code>x</code> and <code>y</code> explicitly. Overloading changes the meaning of the supported expression for that type; it does not make unrelated operations or object identity automatically correct. Equal hash keys must also produce equal hashes.</p><p>Use equality for semantic sameness. A generational handle compares both slot and generation; two spatial point keys compare all key coordinates. Distinct keys may still collide in a hash bucket.</p><UsedLater numbers={['08','23','39','55','60']} /></div>

<div className="foundations-mini" id="lesson-18"><h3>0.18 — Function objects, lambdas and comparators</h3><p>A lambda such as <code>[](const auto&amp; a, const auto&amp; b) {'{'} return a.key &lt; b.key; {'}'}</code> is a callable value. <code>[]</code> lists captures: <code>[x]</code> copies x, while <code>[&amp;x]</code> borrows it and requires x to remain alive. A function object defines <code>operator()</code>, as a custom hash object does. A comparator expresses ordering; a predicate answers a yes/no question. Sorting requires a consistent strict ordering, so equality should not count as “comes before.”</p><p>Canonical merge and DP examples pass a generic lambda an explicit <code>self</code> parameter for recursion; that is C++20 syntax, not the later C++23 explicit-object feature. Capture lifetimes and callable observer constraints matter more here than every possible lambda form. <code>std::function</code> appears as an optional observer wrapper in graph and spatial examples; its callback is instrumentation and must not mutate or reenter the observed operation. <code>std::greater</code> supplies a standard comparison policy for a priority queue of <code>std::pair</code> records.</p><UsedLater numbers={['23','35','41','48','49','63']} /></div>

<div className="foundations-mini" id="lesson-19"><h3>0.19 — Templates instantiate reusable code</h3><p><code>template &lt;typename T, std::size_t N&gt;</code> accepts a type and a compile-time capacity. <code>FixedSlots&lt;int, 3&gt;</code> instantiates one concrete class; <code>FixedSlots&lt;PointKey, 8&gt;</code> instantiates another. <Section id="indexing" number="09" title="A position is valid only under its container's rules." kicker="0.20–0.22 · ITERATORS, INTEGERS AND FINITE VALUES">

<div className="foundations-mini" id="lesson-20"><h3>0.20 — Iterators and standard algorithms</h3><p>An iterator denotes a position. <code>[begin, end)</code> includes the first element and excludes the one-past-end position; do not dereference <code>end()</code>. <code>std::sort</code> reorders a range; <code>std::stable_sort</code> preserves equal elements' original relative order. <code>std::lower_bound</code> and <code>std::upper_bound</code> locate ordered insertion boundaries. Reverse iterators traverse from the back. <code>std::pair&lt;A, B&gt;</code> stores two values and <code>std::tuple&lt;...&gt;</code> stores a fixed group. Their standard comparisons are lexicographic when their elements support comparison. Structured bindings such as <code>auto [distance, vertex] = entry;</code> unpack a pair or tuple. <code>using Entry = std::pair&lt;std::size_t, int&gt;;</code> gives a type another name. Here <code>using</code> is a type alias; <code>using Base::member;</code> in Lesson 0.5 has a different declaration role. <code>std::iota</code> fills a sequence of indices; <code>std::adjacent_find</code> can detect neighboring duplicates after sorting; <code>std::swap</code> exchanges values. A <code>std::vector&lt;bool&gt;</code> is a specialized packed representation, so do not assume its element access is an ordinary <code>bool&amp;</code>.</p><FoundationsLab kind="iterators" /><p><code>vector::erase</code> invalidates iterators and references at or after its position. Reallocation invalidates all. Standard associative containers have different invalidation rules; read their chapter's specific contract before retaining a handle.</p><UsedLater numbers={['16','23','35','48','63']} /></div>

<div className="foundations-mini" id="lesson-21"><h3>0.21 — Integer widths and safe index arithmetic</h3><p><code>std::size_t</code> is an unsigned size/index type; <code>std::uint32_t</code>, <code>std::int32_t</code> and <code>std::uint64_t</code> name fixed-width integer types where available. Unsigned subtraction at zero wraps, so test bounds <em>before</em> computing a heap parent or decrementing a sentinel. Signed arithmetic overflow is invalid. Use <code>low + (high - low) / 2</code> after checking <code>low &lt;= high</code> for a midpoint. For bounded nonnegative ring indices, <code>(index + 1) % capacity</code> wraps when capacity is positive and the addition cannot overflow. <code>std::numeric_limits&lt;T&gt;</code> gives a type’s bounds. A conversion such as <code>static_cast&lt;std::ptrdiff_t&gt;(i)</code> needs a range argument: the destination must represent i before forming an iterator offset.</p><p>C++ integer <code>/</code> truncates toward zero; <code>%</code> gives a remainder with the dividend's sign. Spatial cells need mathematical floor for negative coordinates, so a negative remainder requires adjustment. Chapter 18 intentionally uses defined unsigned wrap for its polynomial hash; Chapter 55 retires generations rather than letting them wrap.</p><FoundationsLab kind="integer" /><UsedLater numbers={['07','09','18','38','55','60']} /></div>

<div className="foundations-mini" id="lesson-22"><h3>0.22 — Floating point and finite coordinates</h3><p><code>double</code> approximates many real values; equality and boundary policy must be chosen deliberately. <code>std::isfinite</code> rejects NaN and infinity before geometry operations. <Section id="reasoning" number="11" title="Predict work and prove the boundary." kicker="0.26–0.28 · COST, INVARIANTS AND VALIDATION">

<div className="foundations-mini" id="lesson-26"><h3>0.26 — Big-O and cost models</h3><p>Let n describe the input size. O(1) stays bounded; O(log n) grows with repeated halving; O(n) scans once; O(n log n) combines levels of work; O(n²) can compare every pair. For n = 8, a full scan checks up to eight items while repeated halving needs only about three reductions. Worst-case, average-case and amortized claims answer different questions. A vector append is amortized O(1), but an individual reallocation may copy or move O(n) elements.</p><div className="foundation-work-bars" aria-label="Illustrative work at input size eight"><p>n = 8 · illustrative units of work</p><div><span>O(1)</span><b style={{width:"2%"}}></b><strong>1</strong></div><div><span>O(log n)</span><b style={{width:"5%"}}></b><strong>3</strong></div><div><span>O(n)</span><b style={{width:"13%"}}></b><strong>8</strong></div><div><span>O(n log n)</span><b style={{width:"38%"}}></b><strong>24</strong></div><div><span>O(n²)</span><b style={{width:"100%"}}></b><strong>64</strong></div></div><p>Auxiliary space excludes the input unless stated. Big-O describes growth, not seconds: allocation, cache locality, branch behavior and constant factors still matter. The book's playback snapshots are teaching overhead, not algorithm workspace.</p><UsedLater numbers={['01','09','38','41','66']} /></div>

<div className="foundations-mini" id="lesson-27"><h3>0.27 — Preconditions, invariants and postconditions</h3><p>A precondition says when an operation may begin, an invariant describes valid persistent state, and a postcondition says what completion guarantees. In a null-terminated doubly linked list, <code>head == nullptr</code> iff <code>tail == nullptr</code>; a nonempty head's <code>prev</code> and tail's <code>next</code> are null. A max heap keeps each parent at least as large as its children. During a multi-step operation, a partial state may temporarily violate the completed invariant; check it at the promised boundary. Guards reject invalid requests; assertions diagnose broken internal assumptions.</p><UsedLater numbers={['03','04','09','21','54']} /></div>
