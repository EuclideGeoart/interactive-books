<Section id="mental-model" number="01" title="The same key follows the same computation." kicker="VISUAL MENTAL MODEL">

```text
"cat" → polynomial-31 → 98262 → mod 8 → bucket 6
"a"   → polynomial-31 →    97 → mod 8 → bucket 1
"i"   → polynomial-31 →   105 → mod 8 → bucket 1  COLLISION
```

A **key** identifies an entry: cat might name a counter. A **value** is the associated payload, such as 42. Hashing uses the key to choose a starting place; it does not hash the mapped value in this map. The hash function returns a full hash value. The capacity tells us how many buckets exist, and modulo reduces the full hash to a valid bucket index.

</Section>
<Section id="intuition" number="02" title="A directory saves searching everywhere." kicker="THE INTUITION">

A list lookup may inspect every key. A hash table first computes a likely location, then resolves any ambiguity there. Determinism means a lookup and an earlier insertion agree about where to begin. Equal keys must produce equal hashes. Different keys may produce the same full hash, and different full hashes can reduce to the same bucket. Neither kind of collision proves equality.

Changing the mapped value should not move the key. Changing capacity may change the bucket even though the key and full hash stay unchanged. Changing the hash policy while entries remain stored would require rebuilding their mapping as well.

</Section>
<Section id="memory" number="03" title="Hash value and bucket index have different ranges." kicker="STRUCTURE / MEMORY LAYOUT">

The canonical function starts at zero. For each ASCII byte it computes `hash = hash * 31 + byte` using unsigned 32-bit arithmetic. Overflow wraps modulo 2³²; TypeScript uses `Math.imul` and `>>> 0` to match that native policy. The result is between 0 and 4294967295. For a positive capacity m, `hash % m` is between 0 and m − 1.

There is no table allocation in this chapter's hash function. The scalar view shows computed values, not object pointers or a claimed native byte layout. Capacity zero is invalid: modulo zero is not an empty-table representation. An empty table still has bucket capacity, but stores no entries.

</Section>

</Section>

<Section id="pointer-trace" number="06" title="Trace arithmetic before tracing pointers." kicker="CODE + VISUALIZATION TRACE">

The first step initializes the canonical hash variable. Each following byte step highlights the multiplication and addition line; the inspector shows the prefix hash and bytes consumed. Returning the full hash does not choose a bucket. The separate mapping line performs modulo. Previous and Reset select immutable snapshots of this computation.

<Section id="invariants" number="07" title="Equal keys must start together." kicker="INVARIANTS">

| Rule | Consequence |
| --- | --- |
| Equal keys imply equal hashes | Insertion and lookup can meet. |
| Equal hashes do not imply equal keys | Compare keys before reading or updating a value. |
| Positive capacity bounds modulo | Every index belongs to the bucket array. |
| Capacity is separate from the full hash | Rehashing can reuse a stored full hash. |
| Hash and equality agree on normalization | A case-insensitive equality needs a compatible hash. |

Our equality is exact lowercase byte equality. If a future key type ignores a field for equality but includes it in hashing, equal keys could be sent to different buckets. That is a correctness defect, not merely poor distribution.

</Section>
<Section id="complexity" number="08" title="Distribution changes how much work follows hashing." kicker="COMPLEXITY EXPLORER">

<HashDistribution id="hash-fundamentals-distribution" />

Hashing a length-L string costs O(L). Index reduction is constant work for these machine integers. A later table operation also pays for collision resolution. The chart selects actual keys under the fixed polynomial and counts actual successful-search comparisons in bucket chains. A long single chain requires a linear scan even though computing its bucket was quick.

Load factor α = n / m measures entries per bucket on average. It does not tell us whether one bucket holds nearly everything. Two maps can have identical size, capacity and load factor but very different search costs.

</Section>
<Section id="break-it" number="09" title="A bucket match cannot stand in for equality." kicker="COMMON MISTAKES / BREAK-IT MODE">

<HashBreakIt id="hash-fundamentals-break" fundamentals />

In the faulty equality scenario, a and i share a bucket but must retain separate values. In the faulty resize scenario, copying bucket indices leaves i in its old bucket after capacity becomes 16. A correct lookup computes 105 % 16 = 9 and would miss it. Restore returns to the valid starting model.

</Section>
<Section id="analogy" number="10" title="A mail sorting rack is a starting place." kicker="REAL-WORLD ANALOGY">

A sorting rule assigns an envelope to a rack. Several recipients may share a rack, so a worker still reads the full address. Adding more racks changes the sorting rule's final reduction; moving the old rack contents straight across by rack number may leave letters in the wrong place.

</Section>
<Section id="engineering" number="11" title="Fast lookup and cryptographic security are different goals." kicker="ENGINEERING INSIGHT">

Hash-table hashing seeks cheap computation and useful distribution for the expected inputs. Cryptographic hashing seeks security properties such as preimage resistance and collision resistance. A fast polynomial with deliberately discoverable collisions does not meet those security goals. A security-sensitive service may also need a keyed or randomized table hash to resist adversarial concentration; this deterministic lesson intentionally makes every run reproducible.

Hash quality depends on the key distribution and capacity policy. A larger table cannot repair every poor hash: distinct keys with the same full hash remain together under every modulo capacity. A production choice needs evidence from its actual workload.

</Section>
