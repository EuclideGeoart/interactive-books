<Section id="mental-model" number="01" title="One page partitions several key intervals." kicker="VISUAL MENTAL MODEL">

A binary search node chooses between two directions. A page with keys 20 and 40 chooses among three intervals: below 20, between 20 and 40, and above 40. Packing several keys and child references into one page reduces the number of levels needed to index a large dataset.

<Section id="intuition" number="02" title="Disk and cache misses make height expensive." kicker="THE INTUITION">

If a lookup must fetch one storage page per tree level, reducing height can matter more than minimizing comparisons inside a page already in memory. A high fanout means that each level covers many more records. B-trees preserve that advantage through occupancy limits and splits, keeping all leaves at one depth.

A B-tree stores records in internal pages as well as leaves: a promoted key moves into the parent. A B+ tree stores records only in leaves. Internal keys are routing copies called separators, and linked leaves support ordered range scans. Finding a separator in an internal B+ page does not mean the record has been reached; equality follows the child on its right.

</Section>
<Section id="memory" number="03" title="Define capacity before reasoning about a split." kicker="STRUCTURE / MEMORY LAYOUT">

The B-tree uses **minimum degree t = 2**. Every nonroot page has 1–3 keys; each internal page has one more child than key, so it has 2–4 children. A nonempty root has at least one key. The root may itself be a leaf; the empty tree has a null root. These are exact conventions, avoiding the ambiguous word order.

The B+ example also permits 1–3 keys in nonroot pages and up to four children internally. This deliberately small top-down variant splits a full leaf's three records into one left record and two right records. A leaf separator is copied from the first record of the right leaf, so that record stays in its leaf. An internal split removes the middle separator from the child and promotes it to the parent. Other B+ implementations choose different leaf capacities and minimum occupancy; their arithmetic must match their split policy.

Pages contain a leaf flag, a vector of integer keys and a vector of child pointers. B+ additionally stores a non-owning next-leaf pointer. The vectors reserve their fixed teaching capacities when the page is constructed. This is a conceptual page model built from C++ objects and vectors, not a packed on-disk layout, disk I/O implementation or durable database format.

</Section>

<Section id="implementation" number="05" title="Preserve ownership while widening the hierarchy." kicker="CANONICAL C++20">

Both headers provide insert, contains, erase, values, empty, clear and valid. They exclusively own pages through child links. Destruction traverses children, never B+ next links. Copy and move are deleted, preventing accidental shared ownership. Search is const and does not alter pages. The shared example needs **both headers** in the same directory; download each complete implementation below.

<CanonicalSource source={plus} main={main} fileName="BPlusTree.hpp" chapter="16" />

The B-tree erases in place, borrowing from a sufficiently occupied sibling or merging minimal children before descent. It collapses an empty internal root onto its only child. The B+ erase deliberately rebuilds from remaining sorted records into a replacement tree, then swaps roots. It is complete and correct, but costs O(n log n) time and O(n) temporary storage rather than logarithmic in-place repair. The browser does not present that rebuild as a local deletion animation.

Allocation safety is explicit. Page construction reserves key/child capacities; construction failure releases partially built vectors. A split allocates its sibling before changing existing pages, then its bounded int/pointer vector mutations cannot allocate. A new root is guarded until its first split succeeds. If a deeper allocation fails, earlier completed splits may have changed shape, but membership and all invariants remain valid. B+ rebuilding erase keeps the original tree until the replacement is ready. Native failure injection checks root and deeper splits under sanitizers.

</Section>
<Section id="pointer-trace" number="06" title="A promoted separator and a published child are different writes." kicker="CODE + VISUALIZATION POINTER TRACE">

The B-tree split saves the full child and median, constructs a right page, copies its high keys, transfers high child links if internal, truncates the left page, inserts the median into the parent, then inserts the right child pointer. A parent can temporarily have the new key without its matching new child link. The live invariant panel makes that incomplete state visible.

A B+ leaf split additionally assigns the new leaf's next link before changing the old leaf's next link. Its promoted separator remains a record in the new right leaf. Internal B+ splits transfer children and move a routing separator upward. A split of the old root completes before the tree publishes its new root; the new page is temporarily reachable through a local pointer rather than the tree's root.

The STL vector insert/assign/resize calls are each one canonical statement. The trace shows page contents at those statement boundaries; it does not invent intermediate internal vector element moves. Likewise, B+ upper_bound and binary_search are standard-library searches within a page, not a promise to animate each library comparator call.

</Section>
<Section id="invariants" number="07" title="Check intervals, occupancy and depth together." kicker="INVARIANTS">

| Settled rule | B-tree / B+ meaning |
| --- | --- |
| Keys in a page are strictly sorted | Duplicates are rejected by the public set API. |
| Child ranges match separator positions | Every descendant belongs in the selected interval. |
| Internal child count is key count plus one | Every interval has one child. |
| Pages respect the defined occupancy bounds | No empty nonroot or overfull page remains. |
| Every leaf has the same depth | Search paths reach the leaf level consistently. |
| Every live page has one owning path | No cycle, lost page or shared owning child exists. |
| B+ separators equal right-subtree minima | Equality routes to the record's leaf. |
| B+ next links match sorted leaf order | Range scan sees each leaf once, then null. |

Pending split states need not satisfy every settled rule. The complete operation must. Non-owning next links do not count as extra owning parents. The B+ checker compares leaf-link order with hierarchy-derived leaf order, so a missing or reordered scan link cannot pass merely because point lookup works.

</Section>
<Section id="complexity" number="08" title="Count page levels separately from in-page work." kicker="COMPLEXITY EXPLORER">

<TreeComplexity kind="btree" />

Search takes logarithmically many levels at fixed fanout. In the native B-tree, an in-page scan costs O(t); the B+ variant uses binary search for routing and leaf lookup. With the teaching capacities fixed, those local costs are bounded. A real large page also spends CPU work shifting keys during insertion. Fanout, packing and access latency determine the practical tradeoff.

A B+ range scan pays one root-to-leaf descent, then scans linked leaves and emits k matching records: O(log n + k) at fixed page capacity, with O(k) result storage. Full values() is O(n). B-tree in-place erase is O(log n) at fixed degree; the explicitly rebuilding B+ erase has the larger cost described above. The explorer's full-page capacity model illustrates height, not actual disk timings or the lab's exact occupancy.

</Section>
<Section id="break-it" number="09" title="Do not remove a B+ record when copying its separator." kicker="COMMON MISTAKES / BREAK-IT EXPERIMENTS">

Compare the split snapshots from both labs. Removing a leaf median as if it were a B-tree record would lose a B+ record. Failing to insert the matching child pointer would leave the parent arity wrong. Following equality left would search the wrong B+ interval. Omitting either next-link assignment could preserve point lookup while breaking range scan.

Pause after promotion and before child publication, and predict the pending rule. Then compare a B+ point search with a range covering the same key. As a native exercise, deliberately clear one leaf link and add an assertion that valid() fails. Semantic tests use that fault to verify the checker without running invalid ownership operations in C++.

</Section>
<Section id="analogy" number="10" title="Read a shelf index before opening another cabinet." kicker="REAL-WORLD ANALOGY">

A cabinet page lists several boundaries so one reading tells you which next cabinet to open. In the B+ arrangement, index cabinets contain directions while all actual records live on ordered shelves. Once you reach the first relevant shelf, a next-shelf link avoids returning to the entrance for every subsequent record.

</Section>
<Section id="engineering" number="11" title="A page-shaped index is not yet a database." kicker="ENGINEERING INSIGHT">

Database and filesystem indexes care about page occupancy, locality, update amplification and range access. A production design also needs serialization, stable page identifiers, crash recovery, concurrency and a reclamation policy. None is supplied by this in-memory teaching container. Leaf links are useful for scans but introduce another relationship that splits, merges and reclamation must maintain.

</Section>
