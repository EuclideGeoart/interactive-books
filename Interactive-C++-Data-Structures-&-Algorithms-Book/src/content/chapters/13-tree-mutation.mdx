<Section id="intuition" number="02" title="Three cases reduce to one vacant or bypassed slot." kicker="THE INTUITION">

A leaf has no children, so its owning slot becomes null. A node with one child is bypassed by writing that child's address into its owning slot. A node with two children cannot simply choose one child and discard the other subtree.

The inorder successor solves the two-child case: it is the minimum of the right subtree, so it has no left child. After copying its integer value into the target, deleting the successor reduces to the zero/one-child case. The successor may be the immediate right child or a deeper left descendant. Its right child, if present, must be reattached.

The duplicate policy remains a set policy. Insert rejects equality before allocation. Copying during erase briefly creates equal stored values, but the completed tree again has strictly ordered, unique keys.

</Section>

<Section id="memory" number="03" title="Owning links are fields; locals are observers." kicker="STRUCTURE / MEMORY LAYOUT">

`Node** slot` identifies the pointer that owns the target: either `root_` or a parent's left/right field. The class stores no parent pointer. `victim`, `successor`, and `replacement` are temporary local observers. `successorSlot` is another pointer to a pointer field, used to splice the successor out of its old location.

Changing a local pointer does not unlink an object. Changing an owning field does not destroy an object. Running a destructor ends object lifetime. Releasing allocation storage is a further phase of delete. Memory view preserves an illustrative tombstone after release, but the inspector refuses to expose former value or child fields.

A root replacement is the same slot mechanism applied to `&root_`. It needs no invented parent node, sentinel Node, or special parent-pointer repair. The only special case is which field's address the local slot holds.

</Section>

<Section id="pointer-trace" number="06" title="The successor's old link must be repaired." kicker="CODE + VISUALIZATION POINTER TRACE">

Search first moves slot through existing root/child fields. After the target is found, `victim = *slot` saves its address. The two-child guard chooses the strategy. Then `successorSlot = &victim->right` starts a leftward search whose every field-address assignment appears separately.

After `successor = *successorSlot`, the line `victim->value = successor->value` changes only the target's integer. Its left, right, and address stay the same. Next, `*successorSlot = successor->right` bypasses the old successor object. The right child survives because the owning slot now targets it. Only then does `delete successor` end lifetime and release storage.

In the zero/one-child branch, replacement first takes victim's left link. If null, it takes the right link. The single write `*slot = replacement` handles a leaf, one left child, one right child, or root replacement. `delete victim` follows. Reading victim's child after delete would be invalid; the canonical order saves everything first.

<Section id="invariants" number="07" title="Temporary disagreement must have a reason." kicker="INVARIANTS">

At the operation boundary, every live node is reachable exactly once, all owning targets are live or null, and all descendant keys obey strict bounds. During successful insertion, the new live node is detached until publication. During erase, a victim is detached before deletion. During successor value copying, two live nodes briefly contain the same key. These are specific pending states, not blanket permission for arbitrary corruption.

A dangling local observer after delete is visible until its actual scope ends. It cannot be dereferenced. A structural link into the same freed allocation would be a failure even mid-operation: the owning links should already have bypassed it. Rewinding selects a saved state; it never resurrects a native object or undoes a real delete.

</Section>

<Section id="complexity" number="08" title="Finding the slot usually dominates rewriting it." kicker="COMPLEXITY EXPLORER">

<TreeComplexity kind="mutation" />

Insert and erase take O(h) search work, with worst-case O(n) on a skewed BST. The successor search adds another downward segment within the same overall height bound. Once the relevant slots are known, a constant number of links and values change. Describing the whole erase as O(1) would omit locating those slots.

Clear rotates left descendants upward until a root has no left child, then deletes it and continues through its right child. Each rotation promotes a previously unpromoted node on this destructive walk, so there are O(n) rotations and exactly n deletions. It uses O(1) auxiliary space and no recursive call stack. It intentionally rearranges a dying tree; ordinary erase does not use this wholesale cleanup strategy.

</Section>

<Section id="break-it" number="09" title="A lost subtree is still allocated." kicker="COMMON MISTAKES / BREAK-IT MODE">

<TreeFoundationsBreakIt ordered />

Lose the left subtree and observe that live allocations remain in memory despite disappearing from root's reachable hierarchy. Free a child before unlinking it and inspect the forbidden structural pointer into ended storage. These are controlled model faults; native undefined behavior is not executed.

In two-child erase, forgetting successor's right child leaks a surviving subtree. Deleting victim after copying the successor value destroys the wrong object. Updating only a local current instead of `*slot` leaves the owner pointing at the removed allocation. Failing to replace root correctly breaks singleton and one-child root cases. Tests cover these boundaries as well as missing keys, duplicates, negative keys, immediate successors, deeper successors, and successor right-child preservation.

</Section>

<Section id="analogy" number="10" title="Replace the label, then remove the spare location." kicker="REAL-WORLD ANALOGY">

Imagine numbered folders arranged by range. To remove a folder with two branches, copy the next folder's number onto the original location, then remove that next location while reconnecting its remaining branch. This illustrates value transfer, not object movement. In C++, the original allocation retains its address; a different allocation is destroyed.

<Section id="engineering" number="11" title="Stable addresses do not guarantee stable values." kicker="ENGINEERING INSIGHT">

A client retaining an observer to the target of a two-child erase can see its key change. A client retaining an observer to the successor sees that object destroyed. This API returns const observers but does not promise the iterator invalidation guarantees of a standard ordered container. The distinction matters when tree nodes also carry external IDs, application handles, or large payloads.

An alternative transplant strategy can move the successor Node into the target's position, preserving the successor's payload identity but requiring more pointer assignments and a different invalidation contract. This chapter deliberately uses one consistent value-copy strategy and tests its exact mechanics. It does not silently substitute transplantation in the visualization. AVL and red-black balancing add more obligations beyond this ordinary BST erase.

</Section>
