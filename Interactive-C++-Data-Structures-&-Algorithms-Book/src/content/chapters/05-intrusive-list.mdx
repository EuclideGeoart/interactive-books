<Section id="intuition" number="02" title="A relationship can borrow an object." kicker="THE INTUITION">

An ordinary owning list commonly allocates a node that wraps each value. An intrusive object contains its own hook fields, so linking can reuse existing storage. That couples the object representation to the lists it may enter, but avoids a separate node allocation for each membership.

The list owns its head and tail variables and controls one hook's relationships. It does not own the object lifetime. Removing an object does not run its destructor, release pool storage, or remove it from unrelated lists. The external owner must unlink every membership before destroying the object.

<Callout title="Stable address is part of the contract." tone="amber">Moving or copying a linked object would leave neighbors pointing to its old identity. This example deletes object and list copy/move operations. A production owner must also choose storage that keeps object addresses stable while linked.</Callout>

</Section>

<Section id="memory" number="03" title="One hook for each independent relationship." kicker="STRUCTURE & MEMORY">

Each `IntrusiveHook` contains prev, next, and an owner/list pointer. The owner pointer records membership even for a single-element list, where both neighbors are null. The object contains three hooks selected by `HookKind`: active, render, and dirty. A list operates on exactly one of them.

| Relationship | Initial example | Independent purpose |
| --- | --- | --- |
| Active | A ⇄ B ⇄ C | Objects participating in an update |
| Render | B ⇄ D | Objects queued for rendering |
| Dirty | A ⇄ D | Objects requiring recomputation |

The fields occupy storage in every object, even while detached. Three hooks mean three sets of links and membership tokens, not three copies of the value. This small fixed example uses an enum and an array; it does not attempt a generalized intrusive-container framework.

</Section>

<Section id="implementation" number="05" title="A non-owning list with explicit membership." kicker="CANONICAL C++20">

The class rejects insertion when this hook already has an owner and rejects removal unless the owner is this exact list instance. Another hook on the same object may still be linked elsewhere. The list destructor calls clear, which unlinks its chain without destroying the objects.

The native example declares objects before lists. C++ destroys local variables in reverse order, so list cleanup runs while the objects are still alive. Object destructors assert that every hook is detached. Assertions document and diagnose this contract; they are not a substitute for a correct lifetime order in release builds.

<Section id="pointer-trace" number="06" title="Unlink is several visible assignments." kicker="CODE ↔ POINTER TRACE">

For a middle object, the predecessor's next first skips the target. The successor's prev still names the target until the second assignment repairs it. Head and tail removal take different branches, updating the corresponding endpoint instead of dereferencing a null neighbor.

The detached object's prev and next are then cleared separately. Its membership owner is cleared last. This publication order makes temporary states visible: an object can be unreachable from head for several statements while its token still identifies the list. Settled invariants must hold when the operation finishes, not after every individual pointer write.

At no point does erase call delete or a destructor. Compare Chapter 3's owning deletion with this trace: unlink mechanics are related, but the ownership consequence is different. Native parity tests observe all three chains and all twelve hooks after every tagged statement, including half-rewired states.

</Section>

<Section id="invariants" number="07" title="A null pair does not prove detachment." kicker="INVARIANTS">

| Invariant at operation boundaries | Meaning |
| --- | --- |
| head is null exactly when tail is null | Empty endpoints agree. |
| head.prev and tail.next are null | The chain has explicit boundaries. |
| next.prev and prev.next point back | Neighbor relationships are reciprocal. |
| A reachable hook names this list as owner | Membership is explicit and specific. |
| A detached hook has null owner, prev, and next | Reinsertion starts from a clean hook. |
| Other hooks are unchanged | Independent memberships remain independent. |

With a singleton, both neighbor pointers are null and owner is non-null. Choose A only, then Insert linked hook. The guard catches the duplicate despite the absence of neighbors. Checking only prev/next would incorrectly accept it and could create self-links or corrupt endpoint state.

</Section>

<Section id="complexity" number="08" title="Count links separately from object management." kicker="COMPLEXITY EXPLORER">

Choose Empty, A only, and A ⇄ B ⇄ C, then compare the counters while pushing D or removing a known member. Rewiring touches a bounded number of fields, so known-object insertion and removal are O(1). Membership checking is a single owner-pointer comparison; no search is needed when you already hold the object reference.

Walking forward or backward visits every member once. The live visit counter grows with the preset's length. During traversal, the inspector exposes the local `current` reference and the diagram marks its target. After return, a scope-end step removes that reference; visited highlights remain as traversal history. Clear repeatedly removes the head, so it is O(n), while each removal remains O(1). The Objects destroyed counter remains zero throughout. Object destruction belongs to the external owner, not this operation's cost.

The `values()` helper collects values into a vector for a convenient demonstration, so it has O(n) output storage and can allocate. Link mutations themselves allocate no nodes. Finding an object by value would still require traversal unless an independent index is available.

</Section>

<Section id="mistakes" number="09" title="Break membership without invoking undefined behavior." kicker="BREAK IT — GUARDED FAILURES">

**Insert linked hook** attempts a second insertion through an already-linked hook. **Remove detached object** attempts removal of D through a list it does not belong to. The canonical guards reject both before writing any links. The native tests also attempt cross-list insertion and removal with two lists selecting the same hook, proving that owner means the exact list instance.

A more dangerous mistake is destroying a still-linked external object. The live browser lab never does that. Its object set stays alive for the whole experiment, and the native example exercises the safe order: lists clear before owners destroy. A dangling neighbor cannot be repaired by checking whether its stored address is non-null.

Reusing one hook simultaneously for two lists would overwrite the first list's relationships. Use separate hooks for independent membership. Separate hooks do not, by themselves, make concurrent access safe; synchronization is outside this single-threaded example.

</Section>

<Section id="analogy" number="10" title="One person, several rosters." kicker="REAL-WORLD ANALOGY">

A workshop attendee may be on an attendance roster, a presentation queue, and a follow-up list. Removing their name from the presentation queue does not remove them from the workshop or the other rosters. Each roster needs its own relationship information.

The C++ difference is physical: those relationship fields live inside the object. If the object disappears while a roster still points to it, the roster now holds an invalid reference. Coordinating the lifetimes is an engineering obligation, not a side effect of changing membership.

</Section>

<Section id="engineering" number="11" title="Separate the scene owner from its work lists." kicker="ENGINEERING INSIGHT">

A scene owner might allocate geometry objects from a pool and maintain active, render, and dirty lists through embedded hooks. Finishing a render task only removes render membership. Deleting a scene object requires removing every membership, ending the object lifetime, and finally returning its storage to the pool.

This is where Chapter 4 and Chapter 5 meet: membership is a third timeline alongside object lifetime and storage lifetime. A stable pool address solves relocation, but not dangling memberships after destruction. An object can be live and detached, live and multiply linked, destroyed with storage reserved, or absent from every list while its storage becomes reusable.

Intrusive lists can reduce allocation overhead and offer predictable rewiring when objects already exist, but they consume per-object space and impose lifetime discipline. Contiguous work queues can have better locality. Choose based on ownership needs, iteration patterns, and measurements, not on the word intrusive.

</Section>
