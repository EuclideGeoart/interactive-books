<Section id="intuition" number="02" title="Monotonicity turns one comparison into many exclusions." kicker="THE INTUITION">
On ascending input, a key smaller than the target proves that all earlier keys are also too small. A larger key proves all later keys are too large. Without that ordering, neither conclusion follows. The prerequisite is a monotonic search domain under the same comparison relation used by the search.

This implementation returns **any match**. In [1A,2B,2C,2D,3E], the first midpoint already matches record C at index 2. It does not promise index 1. A lower-bound algorithm uses a different loop invariant to locate the first not-less-than position; merely renaming this result “first” would be incorrect.
</Section>

<Section id="memory" number="03" title="Bounds move; records stay fixed." kicker="STRUCTURE / MEMORY LAYOUT">
`low`, `high` and `mid` are indices into one unchanged record array. A half-open interval has length high − low and is empty when the two bounds meet. The exclusive endpoint may equal n, but a computed midpoint is always smaller than high while the loop condition holds.

The midpoint is `low + (high - low) / 2`, using integer division. It avoids forming the potentially overflowing sum low + high. Nonnegative ordered bounds make the subtraction valid. The teaching implementation caps n at 64 and uses signed observer indices; the same arithmetic principle applies to larger index types with representable bounds. Ordinary iterative binary search requires O(1) auxiliary memory; stored trace snapshots and input copies are diagnostic overhead.
</Section>

<Section id="implementation" number="05" title="Use one interval convention from start to finish." kicker="C++ IMPLEMENTATION">

The loop runs while low is strictly below high. After a failed equality check, a smaller midpoint key sets low to mid + 1; otherwise high becomes mid. Both updates remove the tested midpoint, and each leaves a valid half-open interval. The found branch returns its midpoint index; an empty interval leaves the result at −1.

The canonical example explicitly checks sortedness for teaching safety. That check is O(n), so **the checked wrapper as a whole is O(n)** for a fresh input, even though the search loop performs O(log n) work. An application that maintains or validates sortedness once can amortize that preparation across many queries. The displayed search counters exclude domain validation and the observer's invariant checks.
</Section>

<Section id="pointer-trace" number="06" title="The branch condition chooses the exact assignment." kicker="CODE + VISUALIZATION TRACE">
With target 40, pause at midpoint index 2. The equality step establishes 30 != 40. The next less-than step establishes 30 &lt; 40. Only the following `binary.low` statement changes low to 3. The discarded left segment now contains keys proven smaller than the target.

When mid is 4, the two tests select the other branch. Setting high to 4 excludes index 4 without also excluding index 3. On the final successful equality, `binary.found` sets result to 3. Bounds need not collapse when a match is found: early return is already justified. Read the source assignment instead of assuming every highlighted range change uses inclusive endpoints.
</Section>

<Section id="invariants" number="07" title="Keep candidates valid and make strict progress." kicker="LIVE INVARIANTS">
The live panel checks ascending input, valid half-open bounds, and discarded ranges. Every discarded left key must be smaller than the target; every discarded right key must be larger. If the target occurs, at least one candidate must remain until a match is reported.

Correct unsuccessful iterations strictly reduce high − low. The variant is a nonnegative integer, so it cannot decrease forever. The diagnostic fault guard also verifies the exact branch update. Any returned index must contain the target; it need not be the first equal position. These are algorithm facts recorded in state, independent of the rendered colors.
</Section>

<Section id="complexity" number="08" title="Logarithmic probes are not always one comparison each." kicker="COMPLEXITY EXPLORER">
<SortingComplexity chapter="38" />
An unsuccessful probe removes at least half the previous candidates, rounded appropriately. For nonempty length n, at most floor(log₂ n) + 1 midpoint probes are needed. Our branch order counts one equality comparison on success and two key comparisons on each unsuccessful probe. Empty input has zero probes and zero key comparisons.

Random access matters. An array reaches its midpoint directly; traversing a linked list to each midpoint does not inherit the same total-time bound. Also keep construction, sorting and validation costs separate from the repeated query cost. These counts are an operation model, not measured CPU time.
</Section>

<Section id="engineering" number="11" title="Preserve the same ordering across production and lookup." kicker="ENGINEERING INSIGHT">
Sorted tables support compact read-heavy indexes, event-time lookup and boundary queries. An engine might sort timestamps once and perform many searches in the resulting array. Mutating an element's search key without restoring order invalidates future binary searches even when the memory remains perfectly accessible.

A comparator must describe the same order during construction and lookup. Reversing sort direction without changing search branches breaks the proof. APIs should distinguish presence queries, any-match search, lower bound and upper bound; the differences matter for duplicate ranges and insertion positions. This chapter implements ascending any-match search only, keeping the contract small and explicit.
</Section>
